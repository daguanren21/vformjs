# 需求下来了，我怎么用这些知识点带 AI 干活

不绑某个仓库、某个表单库。  
场景只有一个：**产品丢来一句话需求，你要用 AI 写代码。**

下面按时间顺序做。每一步对应一个知识点，并写清：**你干什么、让 AI 干什么、停在哪。**

---

## 总览（一张图）

```text
需求一句话
  → ① 进队（别直接开写）
  → ② 问清楚 / 标未知（grill / wayfinding）
  → ③ 写成对错表（行为矩阵）
  → ④ 人批准规格
  → ⑤ 拆成小任务队列（tickets）
  → ⑥ AI 实现（maker）
  → ⑦ 另一套标准验收（checker）
  → ⑧ 人批准提交
  → 全程状态写在文件里，不写在聊天里
```

名词可以忘，顺序尽量别乱。

---

## ① 需求进队：先当「任务卡」，别当「开始写吧」

**知识点：** Loop / Queue —— 工作单位是队列里的任务，不是一轮聊天。

**你做：**

把需求记成一张卡（记事本、Issue、飞书都行）：

```text
标题：……
来源：谁说的 / 链接
现状痛点：用户现在怎么难受
期望：一句话
非目标：这次明确不做的
状态：待澄清
```

**让 AI 做：**

- 可以让 AI 帮你改写成上面的结构  
- **不要**让 AI 这时就改业务代码  

**为什么：**  
一上来就写，会把「产品没说清的事」埋进实现里，后面很难拆。

---

## ② 问清楚：只问「现在必须定」的，装不懂的标出来

**知识点：** grill / wayfinding / fog of war  

**你做：**

对 AI 说类似：

> 这是需求卡。不要写代码。  
> 列出实现前必须拍板的问题，一次给 5～10 个，按依赖分组。  
> 分三类：已能从材料确认的 / 需要我回答的 / 可以以后再定的。

**你回答时：**

- 会的：直接定  
- 不会的：写「未决 + 谁定 + 是否挡住开工」  
- 未决若会改接口/兼容性/迁移：**不能假装已定**

**停在哪：**  
得到一份「已决策 + 未决清单」，仍然没有大段业务代码。

---

## ③ 写成对错表：验收标准先于代码

**知识点：** 行为矩阵；一手材料  

**你做：**

让 AI 根据已决策生成表格：

| 场景（可复现操作） | 现在怎样 | 做成后怎样 | 算不算兼容变化 |
|------------------|----------|------------|----------------|
| …                | …        | …          | 不变/变化/破坏性 |

**你检查：**

- 每一行是不是**能操作、能观察**（点什么、看到什么）  
- 有没有「系统更智能」这种没法验收的空话  
- 未决有没有混进「已批准」列  

**这一步的产出，就是后面 AI 和 review 的共同语言。**

---

## ④ 人批准规格：第一个闸门

**知识点：** 人关口 1（spec 批准）

**你做：**

- 对错表 + 范围/非目标 + 风险，自己或产品过一眼  
- 明确说：**批准 / 驳回 / 先澄清未决**  

**让 AI 做：**

- 批准前可以整理文档  
- **批准前不要实现**  

没过这关就开写，等于授权 AI 用猜测填产品空。

---

## ⑤ 拆任务：小、可完成、可卡住

**知识点：** queue over loops；to-tickets  

**你做 / 让 AI 做：**

把已批准规格拆成 3～7 个小任务，例如：

```text
T1 读代码，标出改动面（只读）
T2 实现主路径
T3 补测试/手测步骤
T4 独立验收
T5 准备提交说明
```

每个任务写清：

- 完成长什么样（证据）  
- 依赖谁  
- 失败了是 `blocked`（记下原因），不是「再试一次」死循环  

**并行可以，但文件别撞车；** 审的人/会话尽量别同时是写的人。

---

## ⑥ AI 实现：给边界，要证据

**知识点：** Skills（流程压缩包）；Harness（真命令真环境）；Maker  

**你怎么下令（示例）：**

> 只做 T2。  
> 依据：对错表第 1～4 行 + 非目标。  
> 不要扩大范围。  
> 做完列出：改了哪些文件、如何按表验证、哪几行还没覆盖。

**你盯住：**

| 要 | 不要 |
|----|------|
| 按表实现 | 「顺便重构」无边界 |
| 跑项目里真实命令 | 只说「应该没问题」 |
| 改不动就 blocked + 原因 | 同一错误空转十几轮 |
| 一手：代码/测试/日志 | 只信 AI 的总结 |

**Skills 在这里的用处：**  
把「怎么澄清 / 怎么写矩阵 / 怎么 review」收成可重复触发的流程；  
**AGENTS.md 在这里的用处：**  
只放仓库导航、命令、死规矩，不把长流程全塞进去。

没有现成 skill 时，就用本文当口令模板，效果同方向。

---

## ⑦ 独立验收：换一顶帽子

**知识点：** Maker ≠ Checker  

**做法（一人也行）：**

1. 新开一个对话（或明确说：你现在是 reviewer，不要改代码）  
2. 只给：对错表 + diff/文件列表 + 测试/手测结果  
3. **不要**给「我已经测过了，你直接过」  

**验收句式：**

```text
通过 / 打回
卡点：
  - 表第 2 行没有证据
  - 超出非目标做了 XXX
```

AI 实现时的自述，不能当验收通过。

---

## ⑧ 人批准提交：第二个闸门

**知识点：** 人关口 2  

自动化可以绿，**能不能合、能不能发** 仍是人定。  
尤其是：对外行为变了、兼容性、数据迁移、权限。

---

## 全程：状态写在磁盘

**知识点：** memory on disk  

聊天会丢。至少留：

```text
docs/ 或 .agent-runs/某需求id/
  需求卡.md
  决策与未决.md
  对错表.md
  任务板.md
  验收记录.md
```

中断一周后：打开这些文件接着干，不要凭记忆续聊。

## 对照表：知识点 → 你实际动作

| 知识点 | 你在干什么 |
|--------|------------|
| Loop | 按状态推进：澄清→批准→实现→验收→提交，而不是单轮 prompt |
| Queue | 任务可排队、可 blocked，不靠无限重试 |
| grill / wayfinding | 先问必答题，未知标未决 |
| 行为矩阵 | 用对错表当合同 |
| Skill | 把重复流程固定成可调用步骤（或固定口令） |
| AGENTS.md | 仓库短索引 + 硬约束，不是第二本百科 |
| Harness | 用真实安装、测试、预览环境验证 |
| Maker / Checker | 写与验分离 |
| 一手材料 | 代码/测试/日志 > AI 总结 |
| 人关口 | 规格批准、提交批准 |

## 复制即用：你对 AI 说的三段话

### 澄清阶段

```text
下面是需求原文：
---
（粘贴）
---
不要写代码。输出：
1) 任务卡（标题/痛点/期望/非目标/状态）
2) 必须拍板的问题（分批，标明依赖）
3) 已确认 / 需我回答 / 未决（未决要写是否挡开工）
```

### 矩阵阶段

```text
根据已确认决策，生成行为对错表：
场景 | 现在 | 做成后 | 兼容性
场景必须可操作可观察。不要写代码。
```

### 实现阶段

```text
规格与对错表已批准（附上）。
只做任务 Tx。
禁止扩大非目标。
完成后给出：改动文件、按表逐行验证结果、未覆盖项。
```

### 验收阶段（新对话）

```text
你是 reviewer，不要改代码。
依据对错表与下列证据（diff/测试输出/手测）给出：通过或打回，列出卡点。
```

## 最小可跑通（赶工期版）

时间紧，至少保留：

1. 非目标写清楚  
2. 对错表 ≥ 3 行  
3. 实现后按表勾一遍  
4. 提交前人看一眼  

可以压缩文档数量，**不要压缩「表」和「两个闸门」。**

---

## 常见失败（对照自检）

| 现象 | 多半缺了哪一步 |
|------|----------------|
| AI 写得很完整但产品说不对 | 缺 ②③④，用猜测填空 |
| 测绿了但行为变了没人知 | 缺对错表 / checker |
| 聊了三天续不上 | 缺磁盘状态 |
| 同一报错修到吐 | 缺 queue/blocked，在死循环 |
| 仓库规则越来越长 | 把流程塞进 AGENTS.md 了，应进 skill/口令模板 |
